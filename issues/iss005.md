# Zadanie 005 — Czytelny wynik i ponowienie w interfejsie

**Typ:** `User Story` | **Stan:** `New` | **Zakres:** etap 5, rdzeń

**Warunek startu:** działające stany decyzji z [zadania 004](iss004.md).

## Opis

Jako osoba obsługująca sprawę chcę rozumieć decyzję bez czytania JSON
i móc ponowić żądanie po błędzie bez utraty tekstu i poprzedniego wyniku.

## Zadanie

- Pokaż polskie podsumowanie i następny krok; JSON zostaw jako szczegół.
- Oddziel transport HTTP od renderowania i stan żądania od wyniku.
- Zachowaj istniejące zabezpieczenia i dostępność formularza.

## Kryteria akceptacji

- Widać decyzję, kategorię, priorytet, zespół, uzasadnienie i brak wysłania.
- Trzy stany decyzji są rozróżnialne bez polegania wyłącznie na kolorze.
- Po błędzie tekst pozostaje; działa ponowienie.
- Poprzedni wynik jest oznaczony jako poprzedni, nie jako nowy sukces.
- Działają klawiatura, fokus i `aria-live`; widok 375 px nie przewija
  się poziomo.
- Wydzielenie HTTP nie zmienia kontraktu; pozostają `textContent`
  i blokada wielokrotnego wysłania.

## Jak sprawdzić

Bez otwierania JSON odczytaj z widoku decyzję, priorytet, zespół i stan
wysłania. Sprawdź sekwencję sukces → nowe żądanie → błąd → ponowienie:
tekst i oznaczony poprzedni wynik pozostają, a ponowienie daje aktualny wynik.
Sprawdź widoczny fokus podczas obsługi klawiaturą i brak poziomego
przewijania przy 375 px według
[etapu 5](../lab.md#etap-5-użyteczny-interfejs-i-k2).

Wykorzystaj trzy przykłady decyzji z briefu i kontrolowany lokalny błąd
dostawcy; osobno sprawdź brak połączenia. Nie wywołuj awarii wspólnej
usługi. Po zmianach uruchom ponownie własny serwer i odśwież widok.
Jeżeli API zwraca błędny kontrakt, wróć do zadania 004 zamiast ukrywać
problem w prezentacji. Test API i zrzut ekranu nie zastępują wykonania
próby ponowienia i obsługi klawiaturą.

**Wymagania:** [protokół użyteczności](../starter/quality-standards.md).
